# Pod·Agent 코드 진단 및 무료 로컬 검증

Updated: 2026-09-15

사용자 요청에 따라 신규 유료 인프라·서비스 도입을 보류하고 기존 코드의 오류 확인을 먼저 수행한다. 이번 작업은 격리된 로컬 데이터와 가짜 외부 응답으로 실행했다. 유료 LLM 호출, AWS 리소스 생성, 운영 Worker 실행, 원본 751 변경, Supabase 마이그레이션은 수행하지 않았다. 기존 인프라 제안은 보존하되 실행 우선순위에서 내렸다.

## 점검 범위

Chief의 실제 실행 분기는 6개이고 PF 전체 검토는 `schemas/orchestration.py`의 27단계다. 화면에 나오는 역할 이름이 모두 별도의 구현 Agent라는 뜻은 아니다. 예를 들어 `PublicFeasibilityAgent`는 현재 개발가능성 평가 함수를 호출하며, 공공정책 전용 시뮬레이션은 구현되지 않았다.

| Pod | 실제 주요 실행 경로 | 이번 확인 사항 |
|---|---|---|
| 토지·법률 | land_review, LegalReview, DevelopabilityScore, LandLedgerEnrichment | 규제 숫자·미확인 값, PNU 연결, 수집 시각, 근거와 승인 상태 |
| 시장·상품 | MarketEvidence, Marketability, ProductPlanning, MarketProductDepth | 비교사례·거리·숫자 파싱, 출처, 근거 부족 상태 |
| 원가·공정 | DevelopmentFeasibility | 원가 입력, 현금흐름 초안의 비용 대사, 부족한 배분 근거 |
| 사업성·현금흐름 | DevelopmentFeasibility, CashFlow engine | 비유한 수치, 총액과 월별 비용, 원본 입력 보존, 부모 계산 연결 |
| PF·신용 | PF 계산, ScenarioEngine, RiskRegister, CreditReview, CovenantEod | 대출 원금, Waterfall 옵션, 미분양 세대 수, 보강 근거, 승인 검토 |
| 공공정책 | 기존 developability use case 재사용 | 구현 범위 표시 및 공통 실행·저장 경계 |

금융, 증거·보고서, AI·Worker 제어는 병렬로 검토했다. 개별 파일과 회귀 테스트의 대응은 [금융 진단](pod-agent-financial-audit-2026-09-15.md), [증거·보고서 진단](pod-agent-evidence-audit-2026-09-15.md), [실행 제어 진단](pod-agent-control-audit-2026-09-15.md)에 기록했다. 이 결과는 모든 입력 조합과 운영 환경의 무결점 증명이 아니다.

## 확인하고 수정한 공통 오류

| 오류 | 수정 후 동작 |
|---|---|
| 실패·취소·빈 Agent 결과를 성공으로 저장 | 실행 상태를 보존하고 정상 완료된 결과만 Pod 산출물로 연결 |
| 내부 예외를 잡은 뒤 부분 산출물을 정상 Pod로 확정 | 자식 Agent 실패를 최종 확정 단계에서도 확인하여 성공 저장 중단 |
| 실패 단계가 완료 목록에 들어가고 미검토 handoff 표시가 사라짐 | 실패·건너뜀 상태를 구분하고 대기 중 사람 검토 표시 유지 |
| 누락된 승인 검토 결과를 통과로 해석 | 알려진 완료 상태만 인정하며 자료 부족은 승인 준비 미완료 |
| 최종 신용 문서 실패 전에 계산한 승인 준비 상태가 남음 | 마지막 단계 실패도 readiness와 보고서 상태에 반영 |
| 실패 실행이 호출자의 프로젝트 입력을 수정 | 복사본에서 실행하고 성공 반환 후 프로젝트 상태 반영 |
| 입력 hash 생성 뒤 중첩 입력이 바뀌어 저장된 snapshot과 불일치 | 실행 전 입력 snapshot을 독립 복사 |
| 중복 Pod 키가 의존성 그래프에서 조용히 소실 | 중복 식별자 입력 거부 |
| 최초 PDF 기준 이미지 생성도 비교 통과로 표시 | `baseline_created`와 실제 `passed`를 분리; 페이지 증감도 회귀로 감지 |
| 금융 입력 오류가 HTTP 500 또는 잘못된 결과로 노출 | 전용 `FinancialInputError`만 HTTP 422로 반환하고 계산 저장 전 차단 |

업무상의 위험 발견(`blocking`, `blocking_issue`)은 분석 자체의 실행 실패가 아니다. 이런 분석은 `completed_with_review`로 남기고 별도의 승인 준비 기준을 적용한다. 임계값·대출 정책·사람의 승인 권한은 새로 만들지 않았다.

Chief 파일에서 호출되지 않는 과거 AI 역할 정의 2개를 제거했다. 실제 사용 중인 역할 정책은 보존했다. 회귀 테스트와 원본 fixture는 삭제 대상 임시 파일이 아니므로 유지한다. 실행 로그와 테스트 생성 파일은 Git에서 제외된 `.runtime`/격리 임시 디렉터리에 남는다.

## 검증

- 신규 공통 실행·API 경계: 23개 통과. 자식 실패 은폐, 실패 후 입력 보존, 승인 결과 누락, hash snapshot, 입력 오류 미저장을 포함한다.
- 웹: `npm run check-types`, `npm run lint` 통과.
- 로컬 전체 API: 2,459개 수집, 2,413 통과 / 6 실패 / 40 건너뜀(510.67초). 40개는 `REALYTICS_TEST_DATABASE_URL` 미설정으로 생략한 PostgreSQL 검사다. 실패는 기존 완료/생략/baseline 기대값, 비용·토지·저장 실행 기록이 불완전한 fixture에 해당했다. 기능 코드는 그대로 유지하고 테스트를 보완한 뒤 관련 45개를 분할 재실행해 모두 통과했다(오케스트레이션·pilot 35개, Chief/API·빈 산출물 7개, 상품별 수금 일정 3개). 부분 테스트 숫자를 전체 통과 수에 중복 합산하지 않는다. 최종 변경 전체의 깨끗한 재실행은 GitHub CI에서 확인한다.
- 기존 테스트가 첫 baseline 생성을 비교 성공으로 기대하던 부분은 새 상태 의미에 맞춰 수정했다. 원가 총액만 있고 실제 비용 항목이 빠진 정상 fixture는 테스트 안에서 비용 근거를 명시한다. 운영 입력·원본에 임의 비용을 채우지 않는다.

## 다음 순서와 남은 제약

1. **무료 로컬 검증을 우선한다.** 수정된 6개 Pod/27단계 통합과 API·웹 검증 결과를 기존 GitHub draft PR #2에 반영하고 CI를 확인한다. 유료 배포는 보류한다.
2. **Coding 작업의 원자적 상태 변경을 구현해야 한다.** 취소와 완료가 경합하면 취소가 덮이는 현상을 메모리 저장소로 재현했다. job/tenant/lease owner/attempt/version을 함께 비교하는 저장소 변경이 필요하다. 이번에는 운영·스테이징 Coding Worker 진입을 차단했으며 경합 자체를 고쳤다고 주장하지 않는다.
3. **Pod의 업무 결과 변경 hash를 분리해야 한다.** 현재 전체 산출물의 실행 UUID가 달라져도 재계산 이벤트가 생길 수 있다. 근거 hash는 유지하면서 업무 결과 비교 계약을 정의해야 한다.
4. **금융 입력의 미정 계약을 확정해야 한다.** 환산 통화·단위, 사용자 지정 Waterfall, 원가 배분은 지원되지 않거나 불완전하면 계산을 거부한다. 일부 시나리오 grid와 0 분모·미적용 구분 등은 금융 진단의 남은 항목을 따른다.
5. **운영 검증은 별도다.** PF 실행과 사람 승인 JSON의 DB 권한 분리, Agent outbox lease/tenant 경계, 실제 sandbox 격리, 원본 증빙·751 검토 및 제한 역할로의 운영 인수는 미완료다. 로컬 성공을 운영 승인으로 해석하지 않는다.

**보고서 비교의 남은 연결:** 현재 PF 실행은 실행별 새 report ID를 사용하므로 최초 baseline을 생성하고 `quality_warning`으로 끝난다. 승인된 기준 보고서/템플릿 버전을 다음 실행에 연결하는 절차와 코드가 필요하다. 기준 이미지를 만들었다는 사실만으로 비교 성공·보고서 승인 준비를 부여하지 않는다.

비용을 줄이기 위해 기존 보안·승인 경계를 생략하거나 공개 무료 호스팅으로 임의 이전하지 않는다. 현재는 추가 서비스 구매 없이 코드 진단과 로컬 검증을 진행할 수 있다.

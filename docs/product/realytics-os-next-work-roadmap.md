## Pod별 자료 수집과 재검토 연결 (2026-11-09 사용자 승인)

사전 검토에서 다중 문서의 전 필지와 기존 검토 입력을 유지하고, 확인된 PNU의
공공 용도지역·공시지가와 시장 비교자료를 수집해 후속 Pod에 전달한다. 같은 입력의
수집 결과는 재사용하며 시간·횟수 제한과 실패 재시도를 유지한다. 수집 지시를 실제
조회 없이 완료로 표시하지 않는다. 공개 조회로 확정할 수 없는 공사 견적·약정·승인
자료는 자동 생성하지 않고 목적과 함께 남은 사용자 확인 항목으로 모은다.

공개 응답·검토 출력은 이번 분석과 재개 상태에서만 사용한다. 토지·법률은 기존 선택
저장 경로를 유지하고 실거래 결과는 저장하지 않는다. 검증은 전 필지 유지, PNU
불일치 차단, 새 근거의 후속 재계산, 동일 입력 재사용, 실패·시간 제한, 원본 무변경을
포함한다. 새로운 DB 스키마·권한이나 유료 모델 호출은 필요하지 않다.
Status: 현재 개발 범위와 다음 작업의 단일 기준

## 운영 업무 완주와 남은 연결 구현 (2026-11-09 사용자 승인)

사용자는 직전 진단의 여덟 범위를 완료할 때까지 이어서 개발하도록 승인했다.
기존 원본·프로젝트·Agent·6개 Chief Pod·27단계와 계산/권한/최종 승인 계약을
보존한다. 구현된 기능을 다시 만들지 않고 운영 자료의 입력 → 수정 → 저장 →
재계산 → 비교 → 초안 → 재열기에서 확인되는 단절을 수정한다.

|---|---|---|

시간 가정은 사실이나 실제 약정으로 자동 생성하지 않는다. 새 가정은 분석용이며
기존 승인 입력·과거 실행·원본 사건/월차를 바꾸지 않는다. 새 금융 수식이나 고급
약정 정책을 추가하지 않고 지원되는 엔진에 명시 입력을 전달한다. 스냅샷 생성과
프로젝트 반영은 각각 명시 행동이며 기존 승인 경계를 우회하지 않는다.

웹·API의 관련 회귀와 실제 자료 대조를 수행한 변경만 기존 브랜치에 커밋·푸시한다.
Vercel과 변경된 API 이미지를 검증하며 main 병합·강제 푸시는 하지 않는다.
신규 유료 인프라·유료 모델 호출은 하지 않는다. 승인되지 않은 DB 구조·권한 변경과
사용자가 직접 수행해야 하는 인증 단계는 필요한 자료를 준비한 뒤 별도로 확인한다.

실제 프로젝트 4의 두 예산·비교·초안 2개·다운로드 10개·재열기와 6 Pod 사전 검토,
비공개 업무 백업·SQLite 격리 복원은 [운영 인수 기록](operating-acceptance-2026-11-09.md)에
정리했다. 보완 자료와 실제 약정·승인은 미확인으로 유지한다. 개인 AI CRUD/RLS는
승인 후 운영에 반영했다. 저장 뒤 legacy 감사 경로의 실패를 정규화 저장으로 수정하고
실제 설정 저장·재조회·감사 기록을 확인했다. 예산 계획 기간·주 결과 우선 표시와
가입/설정/딜룸의 사용자 안내를 관련 회귀와 배포용 빌드에서 확인했다.
새 메일 가입 실사용 시험은 사용자 요청으로 보류한다.

## 사용자 AI·CLI의 운영 Excel 조회 (2026-11-09 사용자 승인)

현재 사용자가 인증한 AI 호스트에서 운영 상봉 문서·실제 후보 31건·원본 셀을 읽는
행동 하나를 완성한다. 기존 `services/mcp-server`의 운영 HTTPS 클라이언트를 확장하고,
프로젝트 목록·문서 목록·페이지 단위 후보·시트·제한된 셀 범위 조회를 MCP와 CLI가 공유한다.
새 연결은 읽기 도구만 노출하며 기존 Agent·6개 Pod·27단계와 계산·승인값을 변경하지 않는다.

인증은 브라우저 쿠키나 다른 Agent의 자격증명을 복사하지 않고 기존 Supabase에서
별도 사용자 세션을 발급받는다. 숨김 입력의 이메일·비밀번호 로그인과 Google 브라우저
S256 PKCE 로그인을 지원한다. Google 전용 계정에 웹 계정 비밀번호를 반복 요청하지
않는다. 기존 127.0.0.1:3000의 고정 복귀 주소로 실제 코드가 도착하고 교환 및 운영
권한 확인까지 성공해야 완료로 처리하며 Auth 설정을 자동 변경하지 않는다. 세션
갱신을 지원하고 비밀값은 Windows 사용자 DPAPI로 암호화해 개인 저장소에만 보관한다.
웹의 공개 CLI 설정은 API 주소·인증기관·publishable 키만 제공한다. 서버 키·DSN·
사용자 토큰은 이 설정이나 MCP 출력에 넣지 않는다. 개인 AI 프로필 DB 권한은 계속 보류한다.

기존 운영 API의 프로젝트·테넌트·근거 읽기 권한과 원본 버전·SHA 검사를 재사용한다.
문서 조회 결과와 후보·셀의 프로젝트/원본이 일치해야 하며 페이지·응답 크기를 제한한다.
읽기 전용 도구 제공은 로그인 토큰 자체의 계정 권한을 축소했다는 뜻이 아니다.
CLI 로그아웃은 해당 CLI 세션과 캐시를 정리하고 웹·다른 사용자 세션은 건드리지 않는다.
지원하지 않는 로그인 경로·만료·갱신 실패·권한 없음은 실제 상태로 안내한다.

완료 기준은 격리 회귀와 실제 계정에서 로그인 → 문서/후보 조회 → 원본 셀 대조 →
재연결을 확인하고, 같은 세션 갱신 경쟁·원본 바뀜·다른 프로젝트·토큰 노출을 방어하는 것이다.
도구 프로토콜과 설치된 Codex의 연결을 검증하되 모델 API의 추가 유료 호출은 하지 않는다.
프로젝트 데이터·DB 구조/권한·Supabase 인증 설정을 새로 바꾸지 않으며 필요한 웹 변경만
기존 작업 브랜치와 Vercel에 배포한다. 자동 CLI 탐지와 웹 실행 버튼은 이 작업에 포함하지 않는다.

현재 검증: 격리 75건과 실제 Google callback·세션 발급·API 본인 권한·갱신을 통과했다.
기존 웹과 같은 자료 계정의 CLI 세션으로 프로젝트 3개·검증 문서 2개·후보 31개를
조회했다. 문서 목록의 전체 파싱 artifact를 메타데이터 요약으로 줄인 뒤 실제 MCP의
문서·후보·시트·셀 조회와 출처/보관 버전·스냅샷 대조를 통과했다. 원본 셀 값과
단위 환산, 대출금 11개 합계 745억 원·미검토 31개·승인 입력 0개, 갱신 후 같은 계정·
공간·후보 재조회를 확인했다. 이 승인 범위의 사용자 행동은 완료했으며 프로젝트
소유권·테넌트 권한·개인 AI 프로필 DB 권한은 변경하지 않았다.

## 문서 후보 검토 흐름 보완 (2026-11-09)

다음 사용자 행동은 기존 웹 문서 검토에서 후보와 실제 원본 값 셀을 함께 확인하고,
작성 사유를 다른 후보에 섞지 않으며, 권한 있는 별도 검토자가 저장한 결정을 다시
열어 확인하는 것이다. 기존 review API를 사용하고 새 쓰기 도구·승인 경로를 추가하지
않는다. MCP는 읽기 전용으로 유지한다.

상봉 브리지는 확인된 추출 규칙·표의 시트/행과 동일 문서의 유일한 셀 근거가 일치할
때 값 셀을 기본 선택한다. 모든 근거와 사용자의 직접 선택은 보존한다. 문서 전환 시
이전 문서의 셀 필터를 해제하고, 사유는 프로젝트·문서·실행·후보별 화면 메모리 초안으로
유지한다. 저장 응답 뒤 재조회가 실패하거나 새 결정 기록을 찾지 못하면 재제출을 막고
사유를 보존하며 재확인을 안내한다. 최신 기록에서 실제 결정을 확인해야 완료로 표시한다.

서버의 생성자/검토자 분리·RBAC·사람 계정·MFA·허용 목록과 검토/계산 입력 선택/최종
승인의 분리는 유지한다. 원본 브리지의 참조 전용·금액 기준 미확인·미래 PF 투영 금지도
보존한다. 운영에서 자동 승인하거나 멤버십·DB 권한을 변경하지 않는다. 합성 별도 검토자
fixture로 저장→재열기와 실패/동시 변경을 검증하고, 실제 운영에서는 읽기·원본 이동만
확인한다. 기존 원본·Agent·6개 Pod·27단계는 보존한다.

로컬 검증: 실제 브리지와 같은 31개 유형 분포·복수 근거를 갖춘 합성 자료의 PC/모바일
44건, 기존 API 검토/승인 경계 12건, 타입 검사·린트가 통과했다. 저장 후 GET 실패와
결정 누락, 작성 중 추가 편집, 403/MFA·409 동시 변경, 불명확한 저장 응답의 재조회 및
자동 POST 재시도 금지까지 확인했다. 금리·금액의 정수 표시와 원본 값 보존을 확인했다.

## Excel 원본 미리보기와 검토 후보 연결 (2026-11-06 사용자 승인)

문서 검토에서 파싱 후보·근거 위치가 없어도 보호된 보관 Excel의 시트 목록과 제한된
셀 범위를 읽을 수 있게 한다. 원본 해시·버전·권한·검역을 검증하고 시트·셀 좌표,
값·수식·저장 캐시·표시 형식을 구분한다. 대용량/희소 시트는 범위 이동과 상한을 제공한다.
현재 브릿지론 현황은 미래 PF 약정과 구분한 실제 출처 기반 후보로 추출한다.
업로드·구조 읽기·후보 추출·미검토·승인 스냅샷을 각각 실제 저장 레코드로 집계하고,
0건에는 미실행·지원 항목 없음·조회 실패·재시도 상태를 구분한다. 읽힌 셀 개수를
파싱 사실이나 승인값 개수로 대신하지 않는다. 원본 열기 → 후보 추출 → 검토/저장 →
재열기를 기존 권한·사람 승인 경계에서 검증하고 원본·계산·DB 스키마는 보존한다.

현재 구현: 후보가 없어도 시트·셀을 읽고 범위를 이동할 수 있다. 기존 추출 프로필을
1.1.0으로 갱신해 상봉 브리지 원본의 명시 항목 31개를 검토 후보로 생성했다.
업로드와 보관 원본 재추출이 같은 버전을 사용하며 구형 결과는 명시적으로 재추출한다.
미검토와 승인 건수는 저장 레코드로 표시한다. 실제 원본의 금액 기준이 확정되지 않은
대출금은 승인 입력 선택을 차단하며, 현재 금융현황을 미래 PF 약정으로 반영하지 않는다.
[열람·검토 계약과 검증](smart-intake.md#excel-원본-열람과-브리지-검토-후보-2026-11-06)을 따른다.

## 운영 지도·3D 가시성 복구 (2026-11-06 사용자 승인)

VWorld 타일 오류를 정상 투명 이미지로 숨기지 않고 원인 분류·재시도·배경 지도 대체로
연결한다. 필지 경계와 선택은 배경 공급자 전환 중에도 보존하며, 지적도·용도지역의
일부 타일 실패와 배경 전체 실패를 구분한다. 서버 키는 브라우저에 전달하지 않는다.
3D는 실제 SDK 초기화·캔버스를 확인한 뒤 준비 완료로 표시하고, 선택 PNU는 해당
프로젝트의 일치 필지 좌표만 사용한다. 위치가 없는 전체 뷰는 사업 위치 미확인인
전국 참고지도로 구분한다. 잘못된 좌표·빈 경계는 확인된 토지로 집계하지 않는다.
원본·저장 정책·테넌트 권한과 기존 무료 운영을 유지하고 관련 회귀·실제 운영 응답을
확인한 뒤 기존 작업 브랜치·Vercel·필요한 Cloud Run 변경을 배포한다.

## 상봉 Excel 재무 매핑 (2026-11-06 사용자 승인)

일반분양·장기민간임대 원본의 개요·사업수지·대출·수금·현금흐름을 구분한
버전 있는 양식 어댑터를 기존 업로드·검토 경로에 연결한다. 파일명이 아니라
시트·표제·단위·주요 행 의미를 확인한다. 원본 파일과 기존 승인값은 보존한다.

완료 기준은 두 원본에서 재무 항목·원 단위 환산·수식/저장값/출처를 추출하고,
소계 중복 없이 매출·사업비를 대사하며, 초기 PF·자기자본·후속 대환을 분리하는 것이다.
임대보증금과 원금 상환은 운영 매출·사업비로 잘못 계산하지 않는다. 임대 분양전환은
원본의 총대금·보증금 정산 관계를 대조해 중복을 막는다. 원본 시트의 기간 단계 카운터와
실제 월을 구분하고 현금흐름의 지급 공사비·원금·자기자본 및 잔액을 각각 확인한다.

화면은 추출된 재무값과 수식 캐시 미검증 상태, 단위와 셀, 대출 단계 및 차이를 표시한다.
사용자가 항목을 골라 검토 입력으로 불러오고 이유와 함께 저장·재열기·재계산할 수 있어야 한다.
전송된 후보 저장은 정식 승인이나 자동 입력 변경이 아니다. 기존 project:analyze·CAS·
원본 무결성·검역과 정식 승인 경계를 유지한다. 원본 수식 오류와 아직 실행하지 않은
Excel 전체 재계산은 명시하며, 검증되지 않은 캐시를 Parser V2 승인 사실로 격상하지 않는다.

기존 PostgreSQL 저장 계약·Parser·검토 API를 사용하고 새 DB 스키마나 유료 조회를
추가하지 않는다. 합성 회귀와 두 실제 원본의 추출·대사·출처·불변성 및 저장/재개를
검증한 뒤 기존 작업 브랜치·Vercel·Cloud Run에 반영한다.

현재 구현: 두 원본의 8개 재무 항목·상품·금융 단계·185/188개월 매핑과 격리 저장/
재열기·계산 검증을 완료했다. [실제 검증과 한계](smart-intake.md#상봉-사업수지-재무-매핑-2026-11-06)를 따른다.
원본 전체 수식 재계산과 실제 대출 약정 검증은 완료로 간주하지 않는다.

## 정식 합의 루프의 독립 재검토 (2026-11-06 사용자 승인)

기존 합의 callback이 이전 토지·시장·사업성 결과를 재사용하던 부분을 공통 독립 평가 경로로 교체했다.
동일한 원본·공공 근거 스냅샷을 사용하되 매 평가에서 지원되는 토지·법률·사업성·
현금흐름·시장·PF·공공성 검토와 데이터 품질·리스크·신용 검토를 실제로 다시 실행한다.
회차별 실행 범위를 입력에 결합해 런타임 캐시의 이전 성공 결과로 대체하지 않는다.
필수 입력이 없는 계산과 미구현 고급 정책은 수행 불가 사유로 남기고 완료로 표시하지 않는다.

기존 27단계·6개 Chief Pod와 승인 권한은 유지한다. 합의 변경안은 승인 전 작업 사본에
적용해 검증하며 원래 승인 입력·정식 계산·보고서에 섞지 않는다. 원래 입력의 독립
재검토 결과와 변경안의 후보 결과를 각각 추적한다. 회차별 입력·출력 해시, 실제 실행,
인계와 교차검사 결과를 기존 합의 산출물에 기록한다. 외부 근거의 신규 조회는 반복
계산과 분리하고 조회 결과를 동결해 회차마다 달라지는 근거를 같은 합의로 취급하지 않는다.

완료 기준은 입력 변경 후 각 실제 Agent 호출과 결과 변화, 같은 회차의 교차검사,
원본·승인 경계 보존, 오류 시 이전 성공값 재사용 금지, 최대 3회·무진행·진동 종료,
미해결 근거·미지원 계산의 명시, 후속 보고서의 입력·산출물 일치를 검증하는 것이다.
관련 API 및 기존 PF 회귀를 통과한 소스만 기존 작업 브랜치와 운영 API에 반영한다.

공개 저장소 전환 후 배포 진행 기록은 [2026-11-03 공개·배포 점검](public-release-2026-11-03.md)에 둔다.
MIT와 기존 공개 사업정보 유지가 승인됐다. GitHub의 코드/CI 배포와 Supabase의 DB/인증 배포,
별도 API/Worker 운영을 구분한다. 기존 시간 기준 입력·저장·재계산 과제와 사람 승인 경계는 유지한다.

### 분석 전 검토와 보완 서류 요청

분석 준비에서 각 Pod는 현재 입력으로 처리 가능한 일, 공식 출처로 자동 확인할 일,
선행 검토가 필요한 일, 사용자 서류가 필요한 일을 구분한다. 검증된 새 결과를
인계한 경우에만 영향을 받는 검토를 다시 평가하고, 새 근거가 없거나 정해진 조회
한도에 도달하면 준비 검토를 마친다. 이후 사용자만 제공할 수 있는 서류를 목적·필지·
필요 항목 기준으로 합쳐 한 목록으로 요청한다. 공통 입력이 전혀 없는 경우에는
분석 전에 원본 자료를 안내한다. 최종 승인 증빙의 부재와 관계없는 검토는 진행 가능 상태로 남긴다.

우선 적용 구간은 토지조서의 전 필지 취합, 필지별 PNU 확인, 일치하는 공공자료의
법률 미리보기다. 미리보기 결과를 근거 없이 저장하거나 승인·보고서 결과로 승격하지
않는다. 6개 Chief Pod의 명시적 사전 검토는 저장 자료와 제한된 공개 근거를 확인하고 기존 인계 형식으로 남은 요청을 정리한다. 실제 Agent 사전 검토와 변경 영향 재실행 연결을 진행한다. 기존 입력·승인 권위를 유지하면서 Legal·Market·Cost·Cash Flow·PF·공공성의 지원 검토를 실제 호출한다. 각 검토의 새 결과를 의존 Pod에 인계하고 의미 있는 입력·결과 해시가 바뀐 항목을 다시 실행한다. 실행 중 조회 실패, 입력 검토 필요, 사용자 제출 필요와 지원 범위를 구분한다.

사전 검토는 한 번에 최대 3회·18개 Pod 호출과 시간 한도로 종료한다. 재개에서도 같은 실행의 한도를 유지한다. 남은 실행이 있으면 보완 목록을 확정하지 않고 계속 확인할 상태를 표시한다. 실행할 작업과 새 근거가 없을 때 관련 Pod·사용 목적·출처와 함께 보완 요청을 정리한다. 공통 원본과 유효한 수동 입력이 모두 없으면 원본 자료부터 요청한다.

조회 결과와 재사용할 상세 산출물은 화면 메모리에 둔다. 서버에는 실행 식별·입력 버전·결과 해시·유효기간의 작은 인계 확인 기록을 저장한다. 후속 요청의 결과 재사용은 해당 프로젝트·사용자의 서버 기록과 대조한다. 입력이 실행 중 바뀌면 오래된 보완 결론을 반영하지 않는다. 페이지 전체 새로고침으로 화면 결과가 없어지면 현재 자료로 새 사전 검토를 실행한다. 브라우저 저장소에 공공 조회 원문을 보관하지 않는다.

검증 범위는 부분 자료에서 실제 Agent 호출, 입력 불변 시 재사용, 비용 변경의 후속 영향, 조회 실패 재시도, 요청 한도와 중단, 권한·출처·재개 해시 변조 및 입력 동시 변경, PC·모바일의 다음 행동과 저장 규칙이다.


## 대시보드 정리 (2026-11-04 사용자 승인)

첫 화면을 프로젝트 재개와 필요한 다음 행동 중심으로 정리한다. 전역 메뉴는
접힌 분석 도구·자료실과 모바일 메뉴로 제공하고, 기존 프로젝트 내부 업무 화면,
6개 Chief Pod·Agent·27단계 PF 흐름은 유지한다. 최근 작업은 6개부터 표시하며
확인 필요/처리 중 필터는 조회된 최근 최대 20개에 한정한다. 전체 프로젝트는
기존 권한 범위 목록을 따로 펼쳐 검색·페이지 이동한다. 미조회는 `—`로 표시하고
실행 상태와 정식 승인은 별도 기록으로 유지한다. 정상 진행을 실행 실패로
취급하지 않으며 실제 실패·차단·반려·보류는 기본 목록에서도 보인다.

처음 접속한 사용자는 두 목록 조회가 정상 완료되어 모두 비어 있을 때만
첫 프로젝트 안내를 본다. 새 업로드는 명시적으로 여는 넓은 작업 창에서 기존
생성·분류·처리를 사용한다. 현재 대시보드에서 닫기/재열기는 File과 진행 상태를
유지하며 분류 실패는 같은 파일로 재시도한다. 처리 중 중복 생성·실행을 막는다.
닫힌 창에서 다른 페이지 링크로 이동할 때 미처리 자료를 알리며, 새로고침·탭 닫기는
브라우저 경고를 제공한다. 브라우저 뒤로가기·프로그램 이동을 포함한 영구 임시저장은
보장하지 않는다. 저장된 원본과 분석 결과는 기존 프로젝트 자료 화면에서 재개한다.

API/DB 계약·계산·증거·권한 정책은 바꾸지 않는다. 기존 전체 목록과 recent-work,
업로드 API를 사용하며 신규 유료 호출·스키마·마이그레이션은 없다. 검증은 최초 진입,
조회 실패/복구, 최근/전체 범위, 권한, 파일 보존/재시도, 모바일 메뉴/검색,
저장된 분석·보완검토 재개를 PC·모바일에서 확인한다. 결과는 아래 구현 현황과
해당 변경 PR에 기록한다.

로컬 검증 완료: 배포용 빌드를 직접 실행한 PC·모바일 관련 회귀 **110개 통과**
(41.2초), API recent-work·intake 관련 10개, 공통 계약 11개 통과. 웹 타입·전체
린트·배포 빌드도 통과했다. 합성 자료로 320/390/1024/1440px 화면과 가로 넘침,
좁은 화면의 버튼 문구·메뉴·업로드 창 포커스를 확인했다. 개발 서버 통합 검사에서는
최초 프로젝트 이동 한 건이 실패했지만 단독 trace와 최종 배포 빌드에서는 통과했다.
원인을 확정하지 않았으며 검사 대기시간만으로 문제를 해결했다고 주장하지 않는다.
실제 사용자 세션·실제 원본 업로드를 새로 검증한 결과는 아니며, GitHub 전체 CI와
Vercel의 해당 커밋 배포 결과는 [변경 PR](https://github.com/parkwh79-stack/real-estate-os/pull/2)에 기록한다.

## 프로젝트 카드와 상단 효과 (2026-11-04)

최근 프로젝트는 일정한 형태의 카드로 구분한다. 모바일은 한 열, 중간 화면은
두 열, 넓은 화면은 세 열이다. 전체 프로젝트 지표는 전체 목록을 펼치고,
확인 필요와 처리 중 지표는 최근 작업의 해당 필터를 선택한다. 조회할 수 없는
지표는 확인 불가 상태를 표시한다. 카드에서 다음 작업과 상세 근거를 찾을 수 있다.

대시보드 제목 영역에 글래스모피즘을 적용한다. 스크롤 패럴랙스는 장식 배경의
이동 폭을 최대 18px로 제한한다. 좁은 화면과 동작 줄이기 설정에서는 배경을
고정한다. 업무 카드와 숫자는 읽기 쉬운 불투명 표면에 표시한다.
`/start`의 ‘대시보드 보기’ 링크는 초기 상태에서 `/dashboard`로 연결한다.
자료를 선택하면 기존 업로드와 재시도 흐름을 지키도록 링크를 숨긴다.

대시보드 업무함 아래의 ‘지도·실거래가’에서 지도를 펼치고, 지역 코드·거래월·
자산 유형·거래 유형을 선택해 국토교통부 실거래가를 조회한다. 조회 결과는
화면 메모리에만 두며 서버 DB·파일·응답 캐시에 보관하지 않는다. 입력 조건을
바꾸면 이전 목록과 지도 핀을 지운다. 제공기관의 오류와 정상 조회 0건을
구분하고, 거래 금액과 면적은 화면에서 정수로 표시한다.
운영 API는 실거래 화면 조회 전용 키를 사용한다. 이 키는 자동 근거 수집 경로를
활성화하지 않으며 실거래 조회에는 프로젝트 읽기 권한이 필요하다.
운영 로그인으로 전국 지도와 국토교통부 아파트 매매 응답을 확인했다.

프로젝트 생성 시 이름을 입력할 수 있다. 비워 두면 첫 원본 파일명에서 이름을
제안한다. 프로젝트 상단에서 쓰기 권한으로 이름을 변경할 수 있고 원본 파일명과
저장된 검토 내용은 그대로 이어서 사용한다. 계정 메뉴와 설정에서 표시 이름을
바꿀 수 있으며, 표시 이름이 없으면 상단에 ‘내 계정’을 표시한다.

## 원본 업로드와 페이지 글자 읽기 (2026-11-04)

2026-11-04 업로드 오류 후속: Vercel 요청 크기 한도를 넘는 원본은 기존 BFF를 통한
3 MiB 분할 전송으로 보완한다. 서버에서 전체 크기·해시·권한·악성 파일 검사를 거쳐
기존 분류/처리로 연결한다. 자세한 전송 상한·수명·운영 범위는 [Smart Intake](smart-intake.md)를 따른다.

저장된 PDF의 원본 보기에서 페이지를 선택해 ‘글자 읽기’를 실행할 수 있다.
기존 ParserAgent가 원문 텍스트를 읽고 스캔이 필요한 페이지만 한국어·영어
로컬 OCR로 처리한다. 결과를 원본과 대조하고 같은 페이지에서 다시 열 수 있다.
판독 결과는 검토 자료로 사용하며 계산 입력에 적용하는 값은 기존 검토 흐름에서 확인한다.

## 자료 입력 조회 복구 (2026-11-04)

운영 PostgreSQL의 프로젝트 화면은 확인된 프로젝트 정보, 원본 목록, 파싱 후보값,
저장된 Pod 산출물을 기존 테넌트 권한으로 조회한다. 저장된 토지조서가 있으면 그
필지와 PNU를 표시한다. 토지 증빙, 가정 승인 이력, 보완 계획을 조회할 수 없는
경우 해당 항목을 미확인으로 표시한다. 부분 응답으로 새 사업 판단을 저장하지 않는다.

조회가 실패하면 ‘다시 불러오기’를 표시한다. 자료 업로드와 별도로 저장한 사업수지
입력은 재시도 중에도 유지한다. 근거가 필요한 보완 계획과 자동 연쇄 실행은 해당
근거가 조회될 때 실행할 수 있다. Vercel 미리보기 도구는 프로젝트 설정에서 숨긴다.

## 본리동 샘플 접수부터 비교 보고서까지 (2026-11-04)

실제 사업수지 XLSX와 같은 사업의 토지조서 XLS를 격리 SQLite에 올렸다. 두 원본의
분류·해시, 저장된 원본 두 건, 토지조서 9필지, 사업수지 출처 셀 미리보기를 확인했다.
원본 수식 오류 37개를 기록하면서 보관된 원본과 해시가 일치하는 사업수지 초안은
검토 후보로 저장한다. 원 단위로 반올림한 값을 출처와 이유를 붙여 저장하고 다시 열었다.
브라우저에서 원본을 올리고, API 재기동 뒤 같은 프로젝트에서 `사업수지!D11`을 근거로
입력을 저장했다. 작업 화면을 열며 갱신되는 파생 그래프가 검토 버전에 섞여 409가
발생하던 원인을 제거했다. 실제 입력 변경은 저장 충돌 검사에 계속 포함한다.

저장한 후보 원본을 기준으로 예산 현금흐름을 계산했다. 원본 기간 64행 중 계산에
사용한 범위는 49행이다. 토지비 1억원 증가 가정을 적용한 실행을 저장하고 비교를
다시 열어 비용 차이 1억원을 확인했다. 원본 사건의 경과 기간이 미확인이라 비교 상태는
부분이다. 선택한 CalculationRun의 보고서와 다운로드 JSON이 일치했다.
두 원본의 SHA-256과 수정 시각은 검증 전후 같았다.

운영 PostgreSQL에서는 기본 트랙 추천을 결정 규칙으로 저장한다. 사업수지 후보·수정
저장의 감사 사건은 기존 정규화 로그에 기록한다. 접수가 완료되면 입력 검토로 이어진다.
실패 파일은 같은 프로젝트에서 재시도하고, 최종 연결 실패는 파일 처리와 구분한다.
자동 처리 경로가 없는 원본은 보관 확인 상태로 표시하여 가능한 자료의 검토를 이어간다.
저장된 토지조서와 아직 보강할 PNU·증빙 상태를 구분한다. 체결 약정과 미조회 토지
증빙은 후속 자료 검토 범위에 둔다.

운영 계정으로 가상 Excel 원본 접수·분류를 확인했다. 분석용 검토 입력 저장의
403을 재현해 저장과 정식 승인의 권한을 구분했다. 분석 권한과 프로젝트 범위 안에서
검토값을 저장하며, 원본 또는 정식 승인값의 승격에는 기존 승인 권한을 적용한다.
운영 배포 후 두 검토값과 출처 셀을 저장하고 같은 프로젝트에서 새로고침해 다시 열었다.
사업성과 현금흐름 화면의 재계산은 검토한 저장값을 기존 결정론 계산 API에 연결한다.
계산 실행 권한과 테넌트 범위를 검증하고, 저장된 CalculationRun을 다시 읽는다.
후속 계산이 일부만 성공하면 그 상태를 표시한다. 월별 금융 검토에는 기존 권한과
입력 확인을 적용한다.

재계산이 저장되면 비교 실행 목록과 저장 버전 확인용 해시를 자동으로 다시 읽는다.
기준안·변경안 선택과 작성 중인 금융 검토 이유는 유지한다. 목록 조회 오류는 계산
저장 결과와 구분하고 다시 불러올 수 있다.

사업성과 현금흐름 상세는 같은 저장 CalculationRun의 수입·지출 막대, 누적 잔액선,
0원 기준선과 근거가 일치하는 최대 부족 시점을 표시한다. 월별 금융 검토의 월말
계정합계와 PF 인출 전 부족액을 구분한다. 원본 사건과 확인된 달력 월차를 별도로
표시하며 미확인 값은 비워 둔다. 비교는 총사업비·개발이익·최대 부족자금의 차이를
보여주고, 두 실행의 달력 기준월과 계산 범위가 일치할 때만 저장된 PF 인출 전
누적 현금흐름을 겹친다. 표와 분석용 초안은 같은 저장 실행을 참조한다.

상환순서·트랜치 회수율·미분양 LTV·할인분양 스트레스는 각각 완료, 자료 필요,
미지원, 오류 또는 미확인으로 표시한다. 완료는 부모 실행 ID와 입력 해시를 모두
대조한다. 기간·상품 구성·대출 조건이 부족하면 해당 입력 검토로 연결한다.
실행 응답에서만 확인된 오류는 새로 열었을 때 저장 근거가 없으면 미확인으로 표시한다.

비교에서는 예비비율과 기준안·변경안에 이미 포함된 예비비, 검토 근거를 입력할 수 있다.
원본에 포함된 예비비를 각각 분리한 뒤, 기준안의 예비비 제외 사업비에 검토 비율을
적용해 원 단위로 반올림한다. 두 예비비 제외 사업비의 증가액을 새 예비비와 비교해
충당 가능액, 잔여액, 초과액을 표시한다. 실제 포함액을 확인한 경우에만 입력하며
포함액이 없으면 0을 명시한다. 선택한 두 계산과 함께 저장하고 검토 초안에 고정한다.
월별 집행 시점은 별도로 확인하며, 비교 차트와 현금흐름은 기존 저장 결과를 사용한다.

## 현재 가입 경로 (2026-11-03 사용자 지시)

회원가입·인증 후 **기본 작업공간 자동 연결 → 대시보드**를 우선한다. 기관 검색,
기관명·사업자번호 입력, 기관 가입 신청·초대·승인은 첫 진입 조건에서 제외하고
후순위 기능으로 보존한다. 기존 신청·프로필·약관 기록은 바꾸지 않는다. 서버가
서명된 계정별로 기본 분석 공간과 역할을 정규 DB에 원자적으로 보관하며, 같은
계정의 중복 생성과 타인 자료 접근을 막는다. 기존 단일 활성 멤버십은 원래 역할로
재사용한다. 새 스키마·DB 권한 확대나 공유기관 자동 승인은 없다.
배포·검증 근거는 [배포 계약](deployment-plan.md)의 최신 후속을 따른다.

## 1. 먼저 만들 제품

**시행·개발 실무자와 PF 검토자가 보유 자료로 사업을 이해하고, 가정을 바꿔 비교하고, 보완할 자료와 검토 초안을 남기는 도구**를 완성한다. 첫 대상은 한 프로젝트를 검토하는 실무자다. 기관 전체의 자동 승인 시스템을 먼저 구축하지 않는다.

핵심 사용자 흐름은 다음과 같다.

```text
프로젝트 생성 또는 재개
→ 사업계획서·사업수지·토지자료 올리기
→ 핵심 숫자와 출처 확인, 누락값은 사용자 가정으로 입력
→ 사업수지·월별 현금흐름·부족자금 계산
→ 공사비·금리·분양가·일정 변경 전후 비교
→ 중요한 위험과 다음 자료 요청 확인
→ 출처·가정·한계를 포함한 검토 초안 저장·다운로드
→ 나중에 같은 프로젝트를 열어 이어서 작업
```

성공은 Agent 수나 화면 수로 판단하지 않는다. 사용자가 중복 입력을 얼마나 줄였는지, 숫자 근거를 찾고 가정을 비교하는 일을 혼자 끝냈는지로 확인한다. 첫 파일럿에서는 수동 작업 시간과 실제 앱 작업 시간을 기록한다. 성능·절감률은 측정 전 약속하지 않는다.

## 2. 구현 판단

### Agent·Pod는 핵심 구조로 유지

사용자가 2026-09-28 재확인한 방향이다. 기존 **6개 Chief Pod, 업무 Agent,
타입이 있는 handoff, 27단계 PF 검토 흐름을 유지**한다. 정리 대상은 사용하지
않는 예제·중복 구현·임시 코드이며, Agent·Pod 체계를 제거하거나 하나의
단순 계산기로 축소하는 작업이 아니다.

| 기존 Pod | 사용자에게 제공할 역할 |
|---|---|
| 토지·법률 | 필지·권리·인허가 근거와 확인할 사항 정리 |
| 시장·상품 | 비교사례, 상품 구성, 가격 가정 검토 |
| 원가·공정 | 비용과 일정 입력 검토, 변경 영향 전달 |
| 사업성·현금흐름 | 수익·월별 자금·부족자금과 가정 변경 비교 |
| PF·신용 | 대출·상환·위험·보완조치 검토 |
| 공공정책 | 현재 개발가능성 평가 범위를 유지하며 공공정책 특화 기능은 검증하며 확장 |

문서 처리·증거·보고서 Agent도 각 단계의 기반으로 유지한다. 먼저 이 구조의
입력과 산출물을 사용자 화면에서 끝까지 연결한다. 별도 Coding Pod 역시
코드를 삭제하지 않으며, 미완료인 운영 활성화만 후순위로 둔다.

### 기능별 진행 결정

| 구분 | 기능 | 진행 결정 |

기존 모듈의 상세 구현 여부는 [현재 구현 현황](current-implementation-status.md)을 따른다. 역사적 문서의 P0와 Done을 그대로 현재 작업 목록으로 복사하지 않는다.

## 3. 다음 구현 순서

### 현재 우선순위: 실제 자료의 입력부터 저장된 비교·다운로드까지

#### 원본 사건·월차 구분과 이자기간 보존 (2026-10-19 최신 후속)

- 본리동 원본 `2.현금흐름`의 F4:I4는 토지계약·교평등·사업승인·분양의 사전 사건
  4개이며 날짜·기간은 없다. J2:BQ2의 1–60을 월 번호의 근거로 읽고 각 원본
  순번·표기·셀 주소와 함께 보관한다. 착공 월 1은 원본 index 4, 준공 월 42는
  index 45에 대응한다. 기존 일정의 1/42와 비용·수금의 원본 index를 임의로
  이동하거나 사건을 모두 M0으로 합치지 않는다. 중복·불연속·누락된 월 번호는
  미확인으로 남기며 과거 저장본에 현재 원본의 월 번호를 소급해서 넣지 않는다.
- 요청·결과의 `periodBasis` v1으로 `source_sequence`와 `calendar_monthly`를 구분한다.
  원본 순서의 예산 CF와 독립 PF 시나리오는 계속 계산한다. 실제 경과 개월이 필요한
  월별 금융 재계산과 기간 스트레스만 해당 사건·셀 및 확인할 이유를 알려주고
  제한한다. 후속 스트레스의 미지원 상태는 다른 계산을 실패로 만들지 않는다.
  명시적 월차 입력과 사용자 분석 가정을 사용하는 기존 월별 금융 정책은 유지한다.
- 본리동 계산은 거래가 있는 마지막 BB열/index 48까지 **49행**이다. 원본 기간은
  **사건 4개+월별 60개, 총 64개**를 따로 보관한다. BC:BQ의 거래 8구분이 모두 0인
  사실과 이월잔액/초기화를 구분한다. 기존 원 단위 검토 입력의 총사업비 **151,841,565,314원**과 금융비용
  예산 **16,298,073,468원**은 그대로다. I97의 `/12*1`은 원본 예산 가정이며 실제
  대출 약정의 이자기간을 확인한 근거로 바꾸지 않는다. 월별 개별 반올림과 총액
  반올림의 기존 비용 1원 차이도 그대로 드러낸다.
- 저장된 계산 행 범위·사건·일정 대응·이자 발생 최초/마지막 월차와 행 수를 화면과
  보고서에 연결한다. 예산 방식은 이자를 재계산하지 않았다고 표시하고, 명시적
  월별 계산의 0금리는 발생 행 0개와 최초/마지막 없음으로 구분한다. 과거 기간 기준
  미기록 실행은 미기록으로 연다. 결과·입력 스냅샷과 과거 hash를 다시 쓰지 않는다.
- 최대부족 위치의 `maxMinusMonth`는 기존 엔진에서 **1기준 계산 행 순번**이다.
  화면·강조 행·사람용 원본 기간 표시는 1을 빼서 실제 행을 찾는다. 원본 JSON과
  계산은 보존하며 사건을 월차로 표시하지 않는다. CF 전체 표는 저장 행을 모두
  표시하고 사업성 화면의 18행 미리보기는 전체 표 링크와 구분한다.
- 선택 실행의 기간 기준을 보고서 본문에 고정하고 재열기·다섯 형식 다운로드에서
  같은 기준인지 검증한다. Word의 CF/수금 표는 원본 순서와 원문 표기를 유지하며
  기간 확인 요약에는 사건의 파일·시트·셀과 일정의 원본 월 번호를 함께 표시한다.
  새 CF 결과는 `cash_flow_engine-v2`, 사업성 Agent는 2.2.0, CF Pod는 1.4.0,
  원가·공정 Pod는 1.3.0으로 이전 캐시를 구분한다. 원본 행이 없는 별도 사업성
  작업 입력에는 원본 사건의 미확인 상태를 전파하지 않는다.

검증: 최종 관련 API 그룹 344개 중 343개가 통과했고, 한 검사는 Windows의
`socket.bind` 자원 부족(WinError 10055)으로 코드 진입 전에 중단돼 단독 재실행으로
통과했다. 마지막 최대부족 위치·Word 표 수정 후 집중 31개도 통과했다(범위 중복).
PC·모바일 72개와 마지막 위치 교정 후 24개, Web 타입·전체 린트가 통과했다.
전체 API·실제 PostgreSQL·브라우저·빌드·정리 검사는 업로드 commit의 PR CI에서
같은 head로 확인한다. 로컬 PostgreSQL 미기동을 실제 저장 검증 통과로 간주하지 않는다.

실제 본리동 원본의 입력/결과를 격리 SQLite에 저장·재열고 JSON과 Word를 대조했다.
**20절·3부록·7개 표와 CF/수금 각 49행을 유지한 31페이지 전체**를 시각 점검했다.
최대부족은 기존 1기준 순번 48, 실제 index 47의 **원본 48: 준공+2**와 같으며
토지계약·사업승인 사건명과 긴 음수의 부호·끝자리가 분리되지 않는다. 잘림·겹침·
깨진 글자·빈 페이지가 없다. 번들 renderer는 LibreOffice 부재로 실패해 별도 숨김
Microsoft Word의 읽기 전용 PDF 출력과 번들 Poppler를 사용했다. 원본 SHA256
`9214afc891530bb369049f9497888d16c4dbeecae69ec1b4c54637d3a61df92f`, 입력·결과 hash와
금리 원값 `0.055`는 유지했다. 최종 DOCX SHA256은
`c83dd1e5473dab07f2a6226400a4988f39aa46ae29087d120fce0dfe0c3738db`다. 이 시각 점검은
실제 약정 승인이나 검토된 운영 PDF 기준과의 비교 통과를 뜻하지 않는다.
결과 기록 후 이번 QA·브라우저 임시 산출물 136개 파일, 104,893,141바이트를 정리했다.
원본 자료·활성 DB·회귀 fixture는 보존했다.

다음 순서: 기존 입력 검토 흐름에서 **날짜 없는 사건의 달력·계산 월차 연결과
분양수금의 분석용 시간 가정**을 명시적으로 확인·저장·재개하도록 이어간다. 실제
대출 개시·만기·상환시점은 현재 sample만으로 확정할 수 없으며, 실제 약정 검증을
완료로 바꾸지 않는다. 다른 보고서 절의 계산/근거 연결과 교차 엔진 금융조건도 남는다.
새 DB 스키마·Supabase 변경, 유료 호출, 원본 수정이나 Agent·Pod 구조 변경은 없다.

#### 일정·분양수금·금융구조 연결과 정수 표시 (2026-10-19 추가 후속)

- 새 선택 계산 초안의 8절 일정·9절 금융구조·10절 분양대금 납입 일정은 선택한
  CF의 저장 입력·결과를 사용한다. `timingBasis` v1에 세 절의 실행 ID와 입력/결과
  hash를 보관하고 재열기·다섯 형식 다운로드에서 본문과 기준을 다시 검증한다.
  CF 미선택은 미확인으로 남기며 현재 프로젝트 자료로 대신 채우지 않는다.
- 일정은 저장 날짜·월차와 명시적 0을 유지한다. 수금은 저장된 계약금·중도금·잔금
  결과를 사용하고, 추정·미승인·누락 상태를 함께 표시한다. 빠진 결과를 CF 행이나
  기본 비율로 재구성하지 않는다. 참여자·배분·PF 구조도 저장 입력에 없는 명칭이나
  계약상 관계·담보권을 추가하지 않는다. 업무 출처는 파일·시트·셀·범위로 표시하고
  내부 경로를 포함한 원시 근거는 계산 스냅샷에 보존한다.
- 사용자가 **금리·비율까지 모두 정수 반올림 표시**를 선택했다. 보고서 미리보기,
  입력 대조·CF 비교 화면과 사람용 다운로드는 금액·수치를 쉼표 있는 정수로,
  소수형 금리·비율은 %로 환산한 정수로 표시한다. 반올림된 비율에는 `약`을 붙인다.
  예: 1,234.5원 → 1,235원, 0.055 → 약 6%. 양·음수의 절반은 0에서 멀어지는
  방향으로 반올림하고 `-0`은 표시하지 않는다. 계산·원본 입력·JSON·hash는 그대로다.
  ID·시각·셀 주소·원본 문자열은 숫자로 해석해 바꾸지 않는다. 기존 봉인된 비교
  Markdown은 저장 당시 문서를 유지하며 새 비교부터 이 표시 정책을 적용한다.
- 저장 보고서의 원본 Markdown은 바꾸지 않고 API의 `report_display_markdown`으로
  미리보기 표시를 제공한다. 결과의 엔진 기본값과 확인된 입력을 구분하는 안내를
  추가했다. 기본값 0을 입력 대조에 새로 넣거나 원본 누락을 해결한 것으로 처리하지 않는다.
- Word 월별 CF·분양수금 표는 모든 저장 행을 유지하며 머리글을 반복하고 행을
  나누지 않는다. 큰 음수의 부호·끝자리가 갈라지던 CF 열 폭을 보완했다. 조회에
  성공하고 근거·지적이 모두 없는 Pod 연결만 절별 자료 요청 표로 줄인다. 조회 실패·
  상태 미기록과 실제 근거·Pod 지적이 있는 부록은 저장된 전체 상세를 유지한다.

검증: 초기 관련 API 121개, 최종 보고서·대조·발행 경계·실제 자료 그룹 206개가
통과했다(범위 중복). 이후 Word의 조회 실패 요약 제한을 보완한 집중 검사 34개도
통과했다. PC·모바일 보고서 브라우저 34개와 Web 타입·전체 린트가
통과했다. 실제 PostgreSQL 저장/재열기 검증은 기존 격리 CI에 연결했다. 전체 CI는
이번 업로드 commit을 기준으로 확인한다.

실제 본리동 원본은 **사전 사건 4행과 월별 60행, 총 64개 기간 행**이며 현재
mapper/engine의 저장 계산은 **M0–M48의 49행**이다. 읽기 전용 대조에서 마지막
거래는 BB열/index 48의 Tr.A 이자 55,000,000원이고, 후속 BC:BQ/index 49–63의
8개 거래 구분 금액은 모두 0이었다. 비용·명시 수금·일정·만기의 마지막 월차로

## 4. 빠르게 만들기 위한 작업 규칙

1. 한 변경은 사용자 행동 하나를 끝낸다. 기존 Agent·Pod의 책임과 연결을 유지하고, 기능을 흉내 내는 새 화면과 호출자가 없는 추상화는 만들지 않는다.
2. 짧은 목적·입출력·저장 위치·완료 기준을 기존 문서에 적고 구현한다. 경미한 수정에 별도 사양서와 승인 회의를 요구하지 않는다.
3. 확인되지 않은 입력은 가정 또는 누락으로 표현한다. 계산 가능한 부분까지 멈추지 않는다.
4. 회귀 위험에 맞는 테스트를 실행한다. 작은 문구 변경마다 전체 서비스를 재검증하는 절차를 추가하지 않는다.
5. 사용하지 않는 코드, 중복 로직, 예제 앱과 임시 산출물은 참조를 확인한 뒤 삭제한다. 회귀 테스트·원본·마이그레이션은 역할이 있으므로 보존한다.
6. 신규 유료 인프라·유료 LLM 호출은 보류한다. 기존 PC와 사용 가능한 환경으로 먼저 사용자 가치를 입증한다.

개발 보조 예약은 사용자의 Codex 앱에서 매일 한국시간 11:30, 12:30, 13:30에
이 대화로 복귀하도록 설정했다. 승인된 작업의 코딩·테스트·GitHub 반영을 수행하고
DB 변경은 검토 후 반영한다. 컴퓨터와 앱이 켜져 있어야 하며, 13:50부터 정리해
14:00에 마치도록 지시했다. 이 지시는 운영체제의 강제 종료 타이머가 아니다.
제품 내부 Coding Pod/Worker를 운영 활성화한 것이 아니며 앱 설정은 Git에 들어가지 않는다.

계산의 정확성·출처·개인정보·최종 승인 권한은 제품 신뢰를 위해 유지한다. 이 경계는 모든 탐색과 초안을 차단하는 이유로 확대하지 않는다.

## 5. 출시와 유지보수 기준

- 로컬 분석 도구: R1–R3의 저장·재개·오류 상태와 관련 계산 회귀 확인.
- 제한된 외부 파일럿: R4에 필요한 실제 인증·데이터 접근·백업·실행 상태 확인.
- 정식 승인·발행: 기존 보고서/권한/증빙 계약에 따른 인수. 기능 개발과 별개로 해당 행위의 기준 적용.
- 결함이 발견되면 먼저 작은 재현과 수정을 완료한다. 배포 전 의존성·접근 권한을 확인하고, 사용 중에는 실패 작업과 계산 지연을 관찰한다. 자료 제공자나 규칙이 바뀌면 영향받는 경로를 확인한다.

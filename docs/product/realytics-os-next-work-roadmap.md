# REALYTICS 제품 실행 계획

Updated: 2026-10-14
Status: 현재 개발 범위와 다음 작업의 단일 기준

## 1. 먼저 만들 제품

**시행·개발 실무자와 PF 검토자가 보유 자료로 사업을 이해하고, 가정을 바꿔 비교하고, 보완할 자료와 검토 초안을 남기는 도구**를 완성한다. 첫 대상은 한 프로젝트를 검토하는 실무자다. 기관 전체의 자동 승인 시스템을 먼저 구축하지 않는다.

핵심 사용자 흐름은 다음과 같다.

```text
프로젝트 생성 또는 재개
→ 사업계획서·사업수지·토지자료 올리기
→ 핵심 숫자와 출처 확인, 누락값은 사용자 가정으로 입력
→ 사업수지·월별 현금흐름·부족자금 계산
→ 공사비·금리·분양가·일정 변경 전후 비교
→ 중요한 위험과 다음 자료 요청 확인
→ 출처·가정·한계를 포함한 검토 초안 저장·다운로드
→ 나중에 같은 프로젝트를 열어 이어서 작업
```

성공은 Agent 수나 화면 수로 판단하지 않는다. 사용자가 중복 입력을 얼마나 줄였는지, 숫자 근거를 찾고 가정을 비교하는 일을 혼자 끝냈는지로 확인한다. 첫 파일럿에서는 수동 작업 시간과 실제 앱 작업 시간을 기록한다. 성능·절감률은 측정 전 약속하지 않는다.

## 2. 구현 판단

### Agent·Pod는 핵심 구조로 유지

사용자가 2026-09-28 재확인한 방향이다. 기존 **6개 Chief Pod, 업무 Agent,
타입이 있는 handoff, 27단계 PF 검토 흐름을 유지**한다. 정리 대상은 사용하지
않는 예제·중복 구현·임시 코드이며, Agent·Pod 체계를 제거하거나 하나의
단순 계산기로 축소하는 작업이 아니다.

| 기존 Pod | 사용자에게 제공할 역할 |
|---|---|
| 토지·법률 | 필지·권리·인허가 근거와 확인할 사항 정리 |
| 시장·상품 | 비교사례, 상품 구성, 가격 가정 검토 |
| 원가·공정 | 비용과 일정 입력 검토, 변경 영향 전달 |
| 사업성·현금흐름 | 수익·월별 자금·부족자금과 가정 변경 비교 |
| PF·신용 | 대출·상환·위험·보완조치 검토 |
| 공공정책 | 현재 개발가능성 평가 범위를 유지하며 공공정책 특화 기능은 검증하며 확장 |

문서 처리·증거·보고서 Agent도 각 단계의 기반으로 유지한다. 먼저 이 구조의
입력과 산출물을 사용자 화면에서 끝까지 연결한다. 별도 Coding Pod 역시
코드를 삭제하지 않으며, 미완료인 운영 활성화만 후순위로 둔다.

## 3. 다음 구현 순서

### R1. 자료에서 숫자 확인까지 — 첫 작업

2026-09-28 사용자가 구현과 GitHub 반영을 승인했다. 첫 변경은 기존 입력 패키지의
사업수지 검토 영역에서 AI 없는 수동 입력, 원본 셀 확인, 수정·가정의 이유 저장,
원 단위 보존, 저장값 재조회와 분석 화면 연결을 제공한다. Parser V2 후보의 정식
승인 편집은 기존 문서 검토 화면을 사용한다. 2026-10-14에는 주요 일정·대출 조건의
편집·저장·재개를 같은 검토 화면과 프로젝트 저장 경로에 연결했다. 실제 자료의
전체 입력 검증과 금리·상환 조건의 월별 계산 연결은 아직 남아 있다.

사용자 문제: 자료를 올린 뒤 어디를 고치고 무엇을 실행해야 하는지 여러 화면을 돌아다녀야 한다.

- 진입: `/project/[id]/input-package`와 `/project/[id]/documents/review`의 기존 흐름을 연결한다. 새 Agent나 별도 프로젝트 데이터 저장소를 만들지 않는다.
- 기존 코드: `use_cases/document_review_workspace.py`, `parser_v2_records.py`, `feasibility_input_builder.py`, `approved_workbook_authority.py`.
- 필수 확인: 프로젝트, 단위, 매출·원가·토지비, 사업기간, 자금조달 입력. 문서에 없는 값은 사용자 입력과 가정임을 기록한다.
- 원본을 덮어쓰지 않고 후보 수정→저장→다시 열기→분석 실행으로 이어지는 다음 행동을 한 화면에서 알 수 있게 한다.
- 외부 AI가 없을 때는 지원 가능한 구조화 Excel·텍스트 자료를 처리하고, 미지원 PDF/OCR은 수동 확인 경로를 제공한다. 로컬 모델 설치나 유료 키 구매를 선행시키지 않는다.

완료 기준: 실제 자료 한 묶음에서 추출값의 원본 위치를 열고, 잘못 읽힌 값 하나를 수정·저장한 뒤 재열어 유지됨을 확인한다. 누락 항목 하나는 명시적 가정으로 분석에 반영되며 증거로 승격되지 않는다. 로컬 테스트는 원본과 분리한 복사본/임시 DB를 사용한다.

첫 변경의 저장 계약:

- 기존 `feasibility-workbook/apply-input`과 프로젝트 저장소를 사용한다. 별도 DB 테이블은 없다.
- `GET feasibility-workbook/review`가 저장값, 항목별 검토 기록, 원본 목록과 검토 hash를 돌려준다.
- 변경된 숫자만 `fieldReviews`, 항목별 `fieldSourceDocuments`, `expectedReviewHash`와 함께 저장한다. 오래된 검토 hash는 409이며, PostgreSQL 동시 쓰기는 기존 프로젝트 버전 검사를 유지한다.
- 입력의 원본은 프로젝트에 보관된 문서로 서버에서 다시 확인한다. 원본 대조 기록도 `needsReview=true`, `approvalStatus=not_requested`이며 승인된 사실로 승격하지 않는다. 승인 workbook 기준값의 우선권은 유지한다.
- 억원 소수 8자리까지 정확히 원 단위로 변환한다. 잘못된 숫자·소수 원·범위 초과·음수 비용을 일부 무시하고 저장하지 않는다. 음수 문서상 이익과 0은 보존한다.
- `manual_review=true` 업로드는 외부 AI를 호출하지 않는다. 선택적으로 기존 AI 추출 경로를 이용할 수 있고, 분할 추출 응답도 표시한다. 미추출 항목은 빈 값으로 남긴다.

2026-10-14 후속 보완은 입력 검토 하단의 분석·문서 검토 이동이다. 수정값이 있으면
버튼이 저장 후 이동 동작으로 바뀌며, 기존 `apply-input` 저장이 성공한 뒤에만 다음
화면을 연다. 입력 오류·저장 충돌이면 값과 이유를 유지하고 이동하지 않는다. 처리 중
중복 저장·이동은 차단하며, 이미 다른 화면으로 이동한 경우 늦은 저장 응답으로 다시
이동시키지 않는다. 수정이 없으면 기존 링크로 바로 이동한다. 항목별 출처와
검토 hash, 사용자 가정의 기존 저장 계약을 그대로 사용한다.

검증: 기존 API 저장·재조회·출처·계산 입력 검사 14개, PC·모바일 브라우저 검사
22개, Web 타입 검사와 변경 파일 린트를 통과했다. 브라우저 초기 시도는 개발 서버
준비·hydration·첫 경로 컴파일 지연으로 시간 초과했으며, 준비된 격리 서버와 작업자
1개에서 상태 대기를 보완한 최종 전체 대상 실행은 모두 통과했다. 저장 성공 후 이동,
입력 오류·409 충돌 시 값 유지, 중복 저장 차단, 화면을 떠난 뒤 늦은 응답을 검증했다.

2026-10-14 기간·대출 편집: 기존 검토 화면에서 주요 일정 6개의 계획일과 대출별
명칭·순위·금액·연 금리·수수료율·만기 개월·상환 재원을 편집한다. 새 일정은 실제
달력 날짜만 입력하고, 금액은 원 단위, 비율은 화면의 %를 API 소수 비율로 바꾼다.
미입력은 null로 남기며 금리·만기·상환 재원을 임의 생성하지 않는다. 기간/대출
묶음별 가정·수정 이유와 원본 셀을 기존 검토 API로 저장한다. 금액과 함께 한 번에
저장하고 검토 hash 충돌·잘못된 입력은 전체 쓰기를 거절한다. 프로젝트의 기존
schedule/pf_structure와 _meta를 사용하므로 새 테이블·마이그레이션은 필요하지
않다. 기존 일정의 추가 항목과 대출별 부가 정보, 승인 정본의 우선권은 보존한다.
저장·재조회·0/누락 구분·출처·오래된 편집·입력 오류·PC/모바일을 검증한다.
금리·수수료 입력의 보존은 월별 현금흐름의 이자·상환 계산 완성을 뜻하지 않는다.
기존 계산 경로의 지원 범위를 화면에서 명시하고 계산 정책 확장은 R2에서 검증한다.

API 확장은 `terms.schedule`(변경한 날짜만), `terms.financing`(행 목록),
묶음별 `termReviews`, `termSourceDocuments`이다. 저장값은 GET의 `terms`와
`termReviews`로 다시 받는다. 검토 hash에는 원시 일정·대출 정보도 포함한다.
대출 삭제·날짜 지우기는 명시적으로 저장하며, 기존 별칭의 과거 값이 되살아나지
않도록 함께 갱신한다. 형식이 잘못되거나 지원 정밀도를 넘은 기존 숫자는
‘원본값 확인 필요’로 표시하고, 사용자가 정정·삭제하기 전 금융 묶음 저장을 막는다.
새 일정 편집은 ISO 날짜만 허용한다. 기존 월차(M0 등)는 원본대로 남긴다.
R1 편집 계약과 별도로 R2 계산 정규화가 기존 숫자·M 월차를 해석한다.

Agent 정규화는 명시적 금리·수수료 0, 선택한 우선순위, 미입력 상환 재원을
유지한다. 금액을 비운 대출이 있으면 PF 금액 의존 지표를 미확인으로 남기고,
필요 항목과 계산 보류 사유를 반환한다. 독립적인 매출·원가 검토는 계속 가능하다.
승인된 canonical 자료와 완전한 별도 시나리오의 우선 실행은 유지한다. 출처가
붙은 일정 객체도 날짜만 읽으며, 지운 일정의 과거 별칭을 재사용하지 않는다.

Supabase 대조: 2026-10-14 프로젝트 ACTIVE_HEALTHY, 로컬·원격 마이그레이션
26개 버전·이름 일치, `naver-userinfo` v1 원격 소스·배포 hash 일치. 이번
편집은 기존 프로젝트 payload를 쓰므로 추가 마이그레이션·함수 배포가 없다.

검증: 관련 API·금융 입력·승인 회귀 156개, PC/모바일 검토 흐름 38개, 공통 계약
9개, Web 타입과 변경 파일 린트 통과. 이전 브라우저 실행 1건은 검토 영역 진입 전
인증 초기화 대기에서 시간 초과했으며, 추적을 켠 개별 재확인과 최종 전체 대상
실행은 통과했다. Windows 전체 API 실행은 초기 진행이 느려 중단했고, 관련
156개는 별도 실행으로 완료했다. 전체 API·브라우저·PostgreSQL 검사는 GitHub
CI에서 확인한다. 이 기록은 실제 운영 DB 쓰기나 실제 사용자 파일럿의 완료가 아니다.

남은 R1 검증은 실제 실무 자료의 전체 입력 묶음과 기간·대출 조건을 함께 재개해
분석하는 것이다. 재현 가능한 소형 workbook의 저장·재조회 테스트를 실제
사용자 파일럿 완료로 간주하지 않는다.

### R2. 가정 변경과 같은 기준의 결과 비교

2026-10-14 병렬 구현 계약: 사용자가 계산 정합성·월별 금융 계산·저장된 비교를
병행하도록 승인했다. 기존 Agent/6개 Pod/27단계를 유지하며 아래 세 작업을 같은
입력 스냅샷과 CalculationRun으로 연결한다.

- 준비도와 현금흐름에서 자기자본·PF·브리지를 같은 분류로 읽는다. 숫자 월차와
  M0/M24, 달력 날짜의 기간 해석을 공통 처리하고 근거 없는 혼합 기준은 거절한다.
- 월별 금융은 사용자가 명시적으로 선택한 검토안으로만 실행한다. 월초 대출잔액에
  연 금리/12 단리, 최초 인출월에 약정한도 기준 수수료, M0 기준 만기월부터 분양대금
  상환계정으로 우선순위에 따라 원금 상환, 비회전 한도를 지원한다. 만기 이후에도
  미상환 원금에 같은 계약금리 단리를 적용하는 검토 가정을 표시한다. 가산 연체금리,
  일수 기반 이자, 변동금리·재인출·별도 상환재원은 이 버전의 지원 범위가 아니다.
  금리·수수료·만기가 없으면 해당 계산을 거절하고 0은 명시적 값으로 보존한다.
- 새 이자·수수료는 기존 예산 금융비용을 대체한다. 예산 원본과 계산 금융비용,
  차이·실효 사업비, 월별 대출잔액·상환액·미충당액을 함께 남긴다. 원금 상환은
  사업비와 분리하고 자금계정과 대사한다. 기존 계산 방식과 승인 정본은 유지한다.
- `cash-flow/run`의 명시적 `reviewedMonthlyFinancing` 요청은 검토 이유와 최신
  검토 hash를 요구한다. 작업 입력으로 별도 후보를 만들고 정책·이유·입력을 기존
  CalculationRun에 저장한다. 승인 정본을 덮어쓰거나 보고서 적격으로 승격하지 않는다.
  기존 일괄 청구액 방식의 후속 시나리오는 새 월별 방식과 일치할 때까지 보류 사유를
  표시한다. 이전 부모 계산의 시나리오를 새 검토안에 재사용하지 않는다.
- 같은 프로젝트에 저장된 두 현금흐름 계산을 선택해 지표와 입력 변경을 비교하고
  선택을 저장·재개한다. 다른 기간은 기간 차이를 표시한 사업 전체 집계 비교만
  허용한다. 원시 입력/출처 hash는 유지하고 실행 UUID·시각만의 차이는 업무 숫자
  변경으로 간주하지 않는다. 비교는 분석용이며 승인·발행 상태를 부여하지 않는다.
- 새 테이블 없이 기존 프로젝트 검토 선택과 계산 저장소를 사용한다. 권한·tenant
  범위·동시 수정 검사·감사 기록을 유지한다. 저장·재조회, 수기 대사한 월별 예제,
  동일 입력 반복, 누락·잘못된 정책·충돌·다른 프로젝트, PC/모바일을 검증한다.

구현 경계: `reviewed_monthly_v1`의 정책 10개 항목은 정확히 일치해야 한다.
착공·준공과 대출 금액·금리·수수료율·만기·지원 상환 재원이 필요하다. 월별 수금의
합계가 총매출과 다르면 자동 비례 조정 없이 보류한다. 미수금·미분양의 별도 계약,
자기자본 추가 납입·사용자 인출표·분할 원금상환은 이 정책에 포함하지 않는다.
알려진 개별 인출·분할상환·이자 자본화·연체가산·변동금리 옵션은 원본 금융 행에서
정규화 전에 검사한다. camel/snake 별칭을 모두 거절해 Agent가 필드를 생략한 뒤
지원되는 단순 조건처럼 계산하지 않도록 한다. 같은 검사를 직접 엔진 요청에도 적용한다.
기존 예산 금융비 배분은 명시 선택하지 않은 경우 그대로 유지한다. 기존 경로에서
착공일이 없으면 준공일 하나를 임의 M0·1개월 사업으로 바꾸지 않고 기존 36개월
호환 기준을 보존한다. 새 월별 모드는 이 호환 기준을 사용하지 않는다.

비교 선택은 프로젝트 `_meta.cashFlowComparison`에 계산 ID와 입력·결과 hash만
저장한다. 최신 500개와 저장된 선택의 과거 계산을 다시 조회할 수 있고, 누락·변경된
계산은 호환 불가로 표시한다. 원시 hash와 출처는 유지하고 실행 ID·시각 및 검토
이유 같은 메타데이터만 업무 차이 표시에서 제외한다. 자료 첨부·비교 선택 기록은
금융 검토 hash를 바꾸지 않지만 상품·수금·원가·canonical 원본 변경은 바꾼다.

기존 `/feasibility/calculate`의 CalculationRun에는 빈 요청이나 override만 남기던
문제를 수정해 프로젝트 기본값과 override를 합쳐 실제 계산에 사용한 입력을 저장한다.
SQLite 호환 경로의 단일 프로젝트 조회는 ID 직접 조회로 바꿨다. 다른 프로젝트의
대형·불량 payload를 읽지 않으며 빈 DB의 JSON 이관은 유지한다. 이는 약 1.65GB
원본 DB의 전체 기동 로딩 개선이나 실제 성능 측정 완료를 뜻하지 않는다.

검증: 관련 API·금융·비교·저장소·프로젝트 CRUD 369개, PC/모바일 고유 64개,
공통 계약 9개와 정리 안전성 6개를 통과했다. 브라우저 최초 실행의 모바일 실패는
넓은 표가 grid의 최소 폭을 늘려 페이지 전체를 가로로 넘치게 한 오류였다.
패널에 `min-w-0`를 적용하고 전체 페이지 폭 회귀를 추가해 정상 클릭을 검증했다.
부모 갱신 알림과 저장 성공 알림이 잠깐 공존하는 테스트 선택도 성공 문구로 좁혔다.
최종 R1 38개와 변경 CF/lineage 26개가 통과했으며 강제 클릭은 사용하지 않았다.
새 월별 표는 PF 포함 수입·원금상환 포함 지출·엔진 순CF·월말 계정합계를 함께
표시하고 누락값은 미확인으로 유지한다. 전체 API·브라우저·PostgreSQL·빌드의
현재 결과는 [PR #2](https://github.com/parkwh79-stack/real-estate-os/pull/2)의
해당 commit CI 검사를 기준으로 확인한다.

2026-10-14 실제 자료 확인: 사용자가 지정한 `sample`의 본리동 사업수지를
격리 저장소에서 업로드하고 원본 셀 네 곳의 값·수식, 정수 원으로 환산되는 일부
금액·일정·대출 조건의 저장·재개, 오래된 입력 409, 원본 다운로드 일치를 확인했다.
요청 override와 저장 입력을 합친 사업성 진단의 CalculationRun도 실제 병합 입력을
보존했다. 원본 파일은 497,028바이트이며 검증 전후 SHA-256이 같다.
원본 수식 캐시에 오류 37개가 있고 수식 재계산은 하지 않았다. 천원 단위 수식값을
원으로 환산하면 원 미만이 남아 전체 검토 입력 저장은 400으로 거절됐다. 임의
반올림 없이 원본을 보존했으며 사용자 처리 기준 확인이 필요하다. 새 월별 계산도
미확인 대출 조건으로 보류하고 계산 기록을 만들지 않았다. 이 결과는 부분 저장과
직접 계산 진단이며 전체 실자료·실사용자 인수 완료가 아니다. 임시 사본·DB는 정리했다.

사용자 문제: 공사비·금리·분양가·일정 변경이 이익과 필요자금에 어떤 영향을 주는지 확인하기 어렵다.

- 기존 Feasibility·Cash Flow·PF 화면 및 결정론 계산 API를 이용한다.
- 입력 단위·기간·CalculationRun·부모 계산 관계를 결과 화면과 다운로드에서 일치시킨다.
- 먼저 기준안과 변경안 두 개를 비교한다. 이후 필요한 경우 하락·회수 시나리오를 확장한다.
- 이익, 최대 부족자금, 월별 CF, 대출·상환 필요량을 설명하고, 계산할 수 없는 지표는 사유와 필요한 입력을 표시한다.
- 재실행 UUID가 바뀐 것과 업무 숫자가 바뀐 것을 구분하는 비교 규칙을 정의한다. 기존 출처 hash는 유지한다.

완료 기준: 동일 입력의 반복 실행은 같은 업무 숫자를 보여준다. 한 가정 변경이 관계된 결과에만 반영되고 두 결과의 입력 기준을 다시 확인할 수 있다. 지원하지 않는 금융 옵션은 임의 기본값으로 처리하지 않는다.

### R3. 보완 요청과 검토 초안

사용자 문제: 결과는 많지만 무엇을 먼저 확인하고 다른 사람에게 어떻게 설명할지 알기 어렵다.

- 기존 Risk·Evidence·Report 화면에서 우선 보완사항, 이유, 연결 문서, 다음 행동을 묶는다.
- 근거가 있는 사실, 사용자 가정, 계산 결과, 미확인 항목을 초안에 구분해 담는다.
- 기존 PDF/DOCX/Excel 생성 경로를 사용하고 동일한 입력·계산 버전을 표시한다.
- 초안을 생성·저장하는 것과 최종 승인·발행 상태를 분리한다. 가능한 분석 초안은 제공하되 승인 상태를 꾸미지 않는다.
- 검토된 PDF 기준 보고서/템플릿을 다음 실행에 연결하는 작업은 이 단계의 보고서 품질 과제로 처리한다.

완료 기준: 초안을 다시 열고 수치 하나를 원본/가정/계산까지 추적할 수 있다. 자료를 추가한 뒤 보완사항과 관련 결과가 갱신되고, 관계없는 기존 검토가 사라지지 않는다.

### R4. 실제 사용자 한 명의 업무로 검증

R1–R3가 끝나면 실무자 한 명이 자기 자료로 “접수→수정→비교→초안”을 직접 수행한다. 막힌 화면·중복 입력·오해한 표현을 기록하고 그 항목부터 수정한다. 사용자가 2026-10-14 지정한 `sample` 폴더의 본리동 사업수지부터 격리 검증하며, 실무자가 직접 수행하는 전체 사용자 인수는 별도다. 원본 751 기록을 임의 승인·복원하거나 정답 fixture로 덮어쓰지 않는다.

외부 사용자가 접속하는 단계에서는 해당 흐름의 계정·테넌트·원본 접근·백업 복구·운영 연결을 검증한다. Coding Worker, 결제, 모든 외부 데이터 제공자의 완성은 이 사용자 검토의 전제조건이 아니다.

## 4. 빠르게 만들기 위한 작업 규칙

1. 한 변경은 사용자 행동 하나를 끝낸다. 기존 Agent·Pod의 책임과 연결을 유지하고, 기능을 흉내 내는 새 화면과 호출자가 없는 추상화는 만들지 않는다.
2. 짧은 목적·입출력·저장 위치·완료 기준을 기존 문서에 적고 구현한다. 경미한 수정에 별도 사양서와 승인 회의를 요구하지 않는다.
3. 확인되지 않은 입력은 가정 또는 누락으로 표현한다. 계산 가능한 부분까지 멈추지 않는다.
4. 회귀 위험에 맞는 테스트를 실행한다. 작은 문구 변경마다 전체 서비스를 재검증하는 절차를 추가하지 않는다.
5. 사용하지 않는 코드, 중복 로직, 예제 앱과 임시 산출물은 참조를 확인한 뒤 삭제한다. 회귀 테스트·원본·마이그레이션은 역할이 있으므로 보존한다.
6. 신규 유료 인프라·유료 LLM 호출은 보류한다. 기존 PC와 사용 가능한 환경으로 먼저 사용자 가치를 입증한다.

개발 보조 예약은 사용자의 Codex 앱에서 매일 한국시간 11:30, 12:30, 13:30에
이 대화로 복귀하도록 설정했다. 승인된 작업의 코딩·테스트·GitHub 반영을 수행하고
DB 변경은 검토 후 반영한다. 컴퓨터와 앱이 켜져 있어야 하며, 13:50부터 정리해
14:00에 마치도록 지시했다. 이 지시는 운영체제의 강제 종료 타이머가 아니다.
제품 내부 Coding Pod/Worker를 운영 활성화한 것이 아니며 앱 설정은 Git에 들어가지 않는다.

계산의 정확성·출처·개인정보·최종 승인 권한은 제품 신뢰를 위해 유지한다. 이 경계는 모든 탐색과 초안을 차단하는 이유로 확대하지 않는다.

## 5. 출시와 유지보수 기준

- 로컬 분석 도구: R1–R3의 저장·재개·오류 상태와 관련 계산 회귀 확인.
- 제한된 외부 파일럿: R4에 필요한 실제 인증·데이터 접근·백업·실행 상태 확인.
- 정식 승인·발행: 기존 보고서/권한/증빙 계약에 따른 인수. 기능 개발과 별개로 해당 행위의 기준 적용.
- 결함이 발견되면 먼저 작은 재현과 수정을 완료한다. 배포 전 의존성·접근 권한을 확인하고, 사용 중에는 실패 작업과 계산 지연을 관찰한다. 자료 제공자나 규칙이 바뀌면 영향받는 경로를 확인한다.

이 문서는 과거 `mvp-definition`, `service-development-roadmap`, `release-plan`, `maintenance-plan`의 역할을 통합했다. 그 문서들의 원문과 이전 로드맵은 [통합 이전 기록](../archive/documentation-baseline-2026-09-28.md)에 남아 있다. 관련 기능 명세는 [전체 문서 지도](../README.md)에서 찾는다.
